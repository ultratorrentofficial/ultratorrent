Torrent Activity Scheduler, phase 4: provider reconciliation, built but not reachable. This is the first scheduler code that can change a torrent, and nothing can run it — the sweep invokes it only for managed mode and that mode is still refused. Deliberate sequencing rather than dead code: the machinery is built and tested a phase before anything enables it, so switching enforcement on later is a change to one guard rather than the arrival of a new body of untested behaviour. No provider interface change was needed; pauseTorrent, resumeTorrent and getTorrent already exist, so the smallest possible surface is used. Three properties matter more than throughput and each has tests. Pauses run before resumes, because resuming first would momentarily exceed the very limit being enforced and, on an engine with its own queue, the resumed torrent would simply be refused a slot. Every action is verified by re-reading state rather than trusting that a call which did not throw did something: a pause that leaves the torrent downloading is counted as unverified, not applied. The subtle case is a resume the engine QUEUES — the provider's own comment documents it, 'a plain resume on a full queue lands it in queued' — where the call succeeded, the torrent is not running, and the engine's own limits are the reason; that is reported as a native queue conflict rather than a success, because claiming otherwise would tell the operator we control a queue that is in fact controlling us. Failures are isolated per torrent, with the reason recorded and not merely the fact, so one 403 does not abandon the rest of the plan. A torrent that vanishes mid-plan counts as done rather than failed, since the desired end state of a pause is 'not occupying a slot' and a deleted torrent satisfies it — alarming there would fire on the ordinary case of someone deleting a torrent. rTorrent's stop and qBittorrent's pause are both accepted as a successful pause, and a resume that lands in checking is accepted as running. 11 unit tests.
