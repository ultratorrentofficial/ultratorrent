Moving a film to another library moves its FOLDER, with everything in it. A movie owns its directory — poster, NFO, subtitles, extras all sit beside the video — so the unit of the move is 'Toy Story (1995)/', not the .mp4 inside it. The previous version joined the target root with the file's BASENAME, so the folder was dropped and the film landed loose in the library root, contradicting the naming template that says a movie's folder follows it; and it moved only MediaFile rows, so every sidecar subtitle stayed behind in the old folder, because subtitles are MediaSubtitle and were never in the move set at all. Artwork with a local path was stranded the same way. Now one atomic directory rename carries the whole folder, and MediaItem, MediaFile, MediaSubtitle and MediaArtwork paths are all rewritten to follow it. The harder half is knowing when NOT to move a folder, since both mistakes destroy something. A folder is moved only where the item genuinely owns it: strictly BELOW the source library root, never the root itself — an item sitting loose in the root has no folder, and treating the root as its folder would move the entire library — and with no item outside the selection living in it, because a TV season folder is shared by every episode and moving it because one was picked would drag the rest into a library they do not belong to. Anything failing those tests falls back to the per-file move, which is what this always did, and so does a cross-device move, since a directory cannot be renamed across filesystems and half-copying a tree is worse than moving the files. Hardlinks survive: renaming a directory entry never breaks the other link, so a Media Intake import keeps its download-side name and goes on seeding untouched — pinned by a test that hardlinks a file, moves the folder, and asserts the link count is still two. An occupied destination folder is refused rather than merged.
