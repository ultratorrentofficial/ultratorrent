A rename that moves a file now removes the torrent that was seeding it. The libraries here live INSIDE the download tree — qBittorrent saves to /downloads and the Movies library is /downloads/Movies/HD Movies — and 3,298 of 3,303 movie files on the live host have a link count of 1. So a rename does not copy anything; it moves the exact bytes a torrent is serving, and nothing ever told the engine. Left alone the torrent finds its files gone, rechecks to 0% and downloads the whole release again beside the copy just organised. It removes the ENTRY, never the data: after the move the payload IS the library's file, so removeTorrentAndData would delete the film that was just organised, and unlike a removed torrent that cannot be undone. Attribution is deliberately narrow because the action is irreversible. A torrent is matched only by contentPath, its own file or folder — never by savePath, which every film in a library shares and which would name all 248 torrents as the owner of one renamed file. A torrent whose contentPath is empty (rTorrent reports none) is skipped rather than guessed at, and containment is compared on whole path segments so 'Movie (2026)' cannot claim 'Movie (2026) Extras'. Where the provenance was recorded at rename time it is used directly, since an exact hash beats any path comparison. Only the relocating modes do this: a hardlink or copy leaves the download where it is, so the torrent goes on seeding and is left alone. The whole step is best-effort — the files are already moved and recorded by the time it runs, so an unreachable engine is logged and the rename still stands rather than being reported as failed. Not gated on the cleanup rules, because this is not tidying; it is the difference between a renamed film and two copies of it. It runs only where the operator opted the library into organising: `autoOrganize` is the permission for the app to move files in that library at all, and removing a torrent follows from that permission rather than being a separate one. `apply` never saw that flag — callers read the library row and pass down derived values (mode, preset, template, libraryPath), and a MANUAL rename is deliberately ungated so an operator can always reorganise by hand. So a hand-driven rename in a library that never opted in still renames, but is not a licence to start deleting from the engine. The lookup resolves the closest enclosing library for the path and fails CLOSED on anything it cannot resolve, since a library nobody configured is not one to act on. A hardlink import is excluded structurally rather than by a rule: Media Intake's library copy is a second name for the same bytes living outside the torrent's own folder, so the contentPath match never reaches it and the download goes on seeding.
