Cleanup policies are built by picking, not by writing JSON. The draft editor was a raw textarea: configuring a policy meant knowing a 63-entry condition catalogue by heart and hand-authoring a document, which is why policies were reported as extremely hard to understand and use. Conditions are now chosen from a grouped, labelled catalogue where every field explains itself inline — the difference between Runtime (what the provider claims) and Duration (what your file measures) is not something anyone guesses. Operators come from the chosen field, so an impossible combination cannot be expressed. Fields that depend on playback history are flagged, because a rule resting on 'never watched' is only as true as your media server's reporting. The action mode explains itself where it is chosen, since it is the difference between a report and an unattended deletion. Two things made this impossible before: the catalogue's 63 label and description keys had never been translated, so nothing could render them; and the client's condition type declared group/label/valueType while the server sends category/labelKey/dataType, so any code reading a label got undefined. Both fixed. Advanced parts the builder does not edit — replacement rules, storage-pressure triggers, nested condition groups — are preserved untouched and reported, never silently rewritten.
