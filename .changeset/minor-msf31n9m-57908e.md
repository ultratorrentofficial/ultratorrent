Per-torrent overrides, so the scheduler's protections can actually be turned on. The planner has honoured protectedFromPause, protectedFromRemoval and forceStarted since phase 2, and nothing could ever set any of them — dormant capability, the same shape of gap as managed scheduling being reachable only by curl. Four kinds, each answering a different question and each explaining its own consequence where it is chosen, because the differences are not guessable from the names. Protect-from-pause keeps a torrent running when the scheduler needs a slot, but it still counts toward the limits and can still be started by the scheduler. Protect-from-removal keeps a seed going past its target. Exclude puts the torrent outside the scheduler's authority in BOTH directions — neither paused nor started — which is why it is modelled as its own occupancy class rather than as another protection flag; conflating them would let an excluded torrent be resumed by a scheduler that was told to leave it alone. Force-start runs it regardless of limits, with the UI saying plainly that the rest of the queue then has that much less room. Overrides are stored apart from the scheduler's own state on purpose: one table records what the scheduler DID, the other what a person WANTS, and clearing the scheduler's memory of a pause must never discard someone's instruction to protect a torrent. Expiry is applied at READ time rather than by a cleanup job, so expiry is a property of the clock and no background task is load-bearing — if it never runs, nothing wrongly stays in force. Re-applying a revoked override revives it rather than colliding with the unique key or leaving a cleared row shadowing the new one. The info-hash is validated for shape before it is stored, since it reaches a provider call eventually. New torrent_scheduler.override permission. 12 unit tests.
