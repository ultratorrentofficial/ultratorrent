Adding a magnet no longer fails with a bare 500. Pasting a magnet into Add Torrent returned 'Internal server error' and nothing else, because the provider threw a plain Error from inside addMagnet. Two separate faults produced that. The parser was narrower than the URIs people actually paste: it matched xt=urn:btih: case-SENSITIVELY, so a perfectly valid magnet:?XT=URN:BTIH:... was unreadable; it never decoded percent-escapes, so a magnet copied out of a redirect (xt=urn%3Abtih%3A...) failed; and it had no notion of BitTorrent v2, whose magnets carry only xt=urn:btmh:1220<sha-256> and no btih at all. The same function existed TWICE, once per engine provider, both copies case-sensitive — while the RSS reader and the Torznab client, which parse the same URIs, both matched case-insensitively, so one magnet could be understood by the half of the app that finds it and rejected by the half that adds it. There is now one implementation in common/magnet.ts, and both providers use it. A v2-only magnet resolves to the truncated v2 hash, the 20-byte form engines report back, so the load-confirmation can match it; a hybrid v1+v2 magnet still prefers v1, the id everything here already keys on. The second fault was the status code: a link the user typed is a client error, not a server fault. The add path already converted a malformed .torrent file into a 400 and simply never did the same for a magnet. It now does, and the message names the actual problem — not a magnet at all (with a pointer to the URL field), an info-hash of the wrong size, or no info-hash parameter — instead of telling an operator the server broke.
