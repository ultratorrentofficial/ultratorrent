A rename now records the torrent its files came from. RenameRequest.hash did two unrelated jobs — choose the file set (ask the engine what that torrent owns) and stamp the operation log — and that overload made it unusable for the post-download pipeline: passing a hash there would have switched gathering away from the library item just identified and enriched, which for a hardlink-import library is a different set of files entirely. So the pipeline passed nothing, and the provenance went with it, even though the torrent that triggered the whole workflow was in scope one call above the rename and used two lines away to fire events. The cost is visible live: on one host all 10,849 rename rows carry a null torrent, and the single automation action that does record one (rename_for_media) has never been configured there. New RenameRequest.sourceTorrentHash carries provenance only — written to the operation row and the audit record, never consulted when building the plan — so a rename can be gathered by path and still say which torrent it came from. MediaProcessingService threads t.hash through media_rename to renameOrMove to renameItem. A library-wide sweep deliberately passes nothing, because it spans every torrent that ever fed that library and one hash would be false for all but one item. Tests pin both halves, including that supplying the hash does NOT turn a path-gathered rename into a torrent-gathered one — the half a future re-merge of the two fields would silently break. This is the linkage a delete needs to know a renamed file is still being seeded; it applies to new renames only, so the existing corpus still needs path-matching against the engine.
